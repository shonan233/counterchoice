\section{Introduction}
\label{sec:introduction}
Modern logic programming languages provide a means for specifying
search spaces with logical rules, which in turn can be used to
procedurally generate artifacts across diverse artistic domains, including
maps for fictional worlds, architectural structures, and musical
compositions.  % TODO add citations
However, the foundation they provide is only a starting
point for pragmatic tools that support creative practices specific
to these domains. 
Formal logic may be as flexible as a paintbrush, as aesthetically pleasing
as a sestina, and as expressive as musical staff notation, but provides a
very different interface for experimentation and creative decision-making.
Complementary work on {\em creativity support
tools}~\cite{shneiderman2002creativity}, 
{\em casual creators}~\cite{compton-casual}, 
and {\em narrative instruments}~\cite{kreminski2021toward}
suggest that these differences meaningfully
affect the audiences and practices that they
enable.

Our work is thus motivated by a broader goal to understand how {\em tools},
{\em instruments}, and {\em notations} can be built atop expressive
computational and logical foundations to better understand how those
foundations support specific creative practices.

This paper presents \emph{CounterChoice}, an experiment with 
using a modern logic programming language to generate first-species
counterpount compositions, as a case study.
Our experiment has resulted in a graphical tool for generating
first-species counterpoint compositions: the user enters the first voice of
the composition (the \emph{cantus firmus}), and a logic program
automatically synthesizes a second voice to complete the composition (the
\emph{counterpoint}). We wrote the logic program, which encodes the musical
principles of counterpoint, in the finite-choice logic programming language
\emph{Dusa} Developed in response to the promise and limitations of
answer-set programming (ASP), Dusa supports constraint-intensive
search-based generative problems like counterpoint composition, but it is
so new that it lacks established demonstrator applications.  Counterpoint
synthesis is an appropriate case study because the search is large enough
to pose a computational challenge and the problem constraints are
sophisticated but widely agreed-upon since counterpoint is a standard topic
in formal music theory education.  Counterpoint and other harmony exercises
in general are so clearly constraint-solving problems that one of the
authors daydreamed ${\approx}14$ years ago of solving her Harmony homework
in Prolog. Years later, logic programming technology has advanced to make
this daydream possible.

A single case study holds multiple lessons when viewed through different
lenses.  The CounterChoice case study seeks to address the following
research questions (RQs):

\begin{itemize}
  \item \textbf{RQ1:} When we attempt to express the principles of counterpoint
    as ``executable knowledge''~\cite{harmer2012executable} in a logic
    programming language, how does the computational formalism compare with
    the musical formalism?
  % \item \textbf{RQ2:} When the expression of these principles needs to
  %  be adapted for efficient counterpoint synthesis, how does this change
  %  affect the relationship between computational and musical formalism? 
  \item \textbf{RQ2:} How easily and modularly can a mixed-initiative 
    creative interface~\cite{deterding2017mixed}
    be developed for the Dusa solver that supports
    familiar affordances and notation for music
    composition without modifying the underlying language?

  \item \textbf{RQ3:} What does this case study reveal about the existing
    capabilities of Dusa, and opportunities for improved language runtime
    and tool support, in the context of constraint solving for an artistic
    practice?

  % \item \textbf{RQ2:} How much of the tool implementation can readily be performed in Dusa, and how much must be performed in traditional languages?
  % \item \textbf{RQ3:} How might the tooling of Dusa and similar languages be revised to simplify the development of user-facing generation tools?
\end{itemize}

Answering RQ1 helps us understand the adequacy of logic for formalizing harmony, i.e., whether music theory relies on rules that cannot be formalized.
Answering RQ2 helps us characterize the extent of productivity gains associated with specialized languages.
Answering RQ3 provides formative feedback to guide continuing development of the Dusa language and promote future application development.
