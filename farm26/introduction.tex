\section{Introduction}
\label{sec:introduction}
Modern logic programming languages provide a means for specifying
search spaces with logical rules, which in turn can be used to
procedurally generate artifacts across diverse artistic domains, including
maps for fictional worlds~\cite{smith2011answer,carpenter-tile,madkour2023probabilistic}, architectural
structures~\cite{wonka2003instant,muller2006procedural,van2020declarative},
and musical compositions~\cite{boenn-asp,everardo2011armin}.
However, the foundation they provide is only a starting
point for pragmatic tools that support creative practices specific
to these domains. 
Formal logic may be as flexible as a paintbrush, as aesthetically pleasing
as a sestina, and as expressive as musical staff notation, but provides a
very different interface for experimentation and creative decision-making.
Complementary works on {\em creativity support
tools}~\cite{shneiderman2002creativity}, 
{\em casual creators}~\cite{compton-casual}, 
and {\em narrative instruments}~\cite{kreminski2021toward}
suggest that these differences meaningfully
affect the audiences and practices that they
enable.

This paper presents \emph{CounterChoice}, an experiment with using a modern
logic programming language to generate musical compositions\footnote{This seems to be an evergreen pursuit; e.g., Ovans and Davison created a graphical counterpoint editor to exercise Echidna over 30 years ago~\cite{ovans-interative}!}, as a case study in
understanding how {\em tools}, {\em instruments}, and {\em notations} can be
built atop expressive computational and logical foundations to better understand
how those foundations support specific creative practices.

CounterChoice consists of a graphical tool for generating first-species
counterpoint compositions, backed by a set of declarative rules encoding the
musical principles of first-species counterpoint, written in the finite-choice
logic programming language \emph{Dusa} \cite{martens2025finite}. In this
graphical tool, the user enters the first voice of the composition (the
\emph{cantus firmus}), and our logic program automatically synthesizes a second
voice to complete the composition (the \emph{counterpoint}).

Developed in response to the promise and limitations of
answer-set programming (ASP), Dusa supports constraint-intensive
search-based generative problems like counterpoint composition, but it is
so new that it lacks established demonstrator applications.  
Counterpoint synthesis is an appropriate case study
because the search space is large and sophisticated,
yet the problem constraints are widely agreed-upon because counterpoint is a standard topic
in formal music theory education.  Counterpoint and other harmony exercises
are so clearly constraint-solving problems that one of the
authors daydreamed over a decade ago of solving her Harmony homework
in Prolog. Years later, logic programming technology has advanced to make
this daydream possible.

A single case study holds multiple lessons when viewed through different
lenses.  The CounterChoice case study seeks to address the following
research questions (RQs):

\begin{itemize}
  \item \textbf{RQ1:} How faithfully is the established musical formalism of counterpoint reflected in the computational formalization of counterpoint as ``executable knowledge''~\cite{harmer2012executable} in a Dusa program?
  % \item \textbf{RQ2:} When the expression of these principles needs to
  %  be adapted for efficient counterpoint synthesis, how does this change
  %  affect the relationship between computational and musical formalism? 
  \item \textbf{RQ2:} How does development of a mixed-initiative creative 
    interface~\cite{deterding2017mixed} with familiar 
    composition affordances interdepend with the 
    development of the Dusa backend solver? 
%  How easily and modularly can a mixed-initiative 
%    creative interface~\cite{deterding2017mixed}
%    be developed for the Dusa solver that supports
%    familiar affordances and notation for music
%    composition without modifying the underlying language?

  \item \textbf{RQ3:} How can the experience of developing CounterChoice 
    inform the design and implementation of programmer experience for logic 
    programming languages, in the context of constraint solving for an artistic
    practice?
 
  % \item \textbf{RQ2:} How much of the tool implementation can readily be performed in Dusa, and how much must be performed in traditional languages?
  % \item \textbf{RQ3:} How might the tooling of Dusa and similar languages be revised to simplify the development of user-facing generation tools?
\end{itemize}

Answering RQ1 helps us assess the cost and value of choosing Dusa vs.\ other programming languages by understanding whether the desired domain concepts can be expressed, and with what difficulty.
Answering RQ2 helps us assess both the flexibility and uniqueness of Dusa as a development platform.
On one hand, a flexible programming language should require few or no changes to support the development of a new application.
On the other hand, if Dusa provides unique features, the impact thereof should be visible in the interface.
Answering RQ3 contributes to the shared knowledge of the logic programming community beyond Dusa by providing design and implementation recommendations.
