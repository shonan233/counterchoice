\subsection{Research Questions}
We structure the discussion of our experience building and using CounterChoice around our research questions.
We answer each question in turn by synthesizing the empirical results of the development process with the authors' qualitative experiences as the developers.

\paragraph{RQ1: How faithfully is the established musical formalism of counterpoint reflected in the computational formalization of counterpoint as ``executable knowledge'' in a Dusa program?}
At the top-level, the Dusa formalism is structured as \verb|#forbid| and \verb|#demand| constraints.
These constraints match the formalism of natural-language counterpoint rules directly, which define patterns that must or must not occur.

Dusa formalism and counterpoint formalism differ primarily in their depth.
As a natural-language description, the rules of counterpoint can freely assume domain knowledge: the intended readers understand the concepts of notes, intervals, modes, and direct vs.\ contrary motion.
Dusa is not a domain-specific language, so these notions must be implemented explicitly.
The implementation in Dusa was concise precisely because the domain concepts can be built up readily from concepts native to Dusa, such as finite types and natural numbers.

Students of music theory traditionally prefer to use one formalism at a time, providing a unified guiding structure for the composition.
In contrast, we need to ensure that the Dusa implementation of counterpoint concepts is faithful.
We found it helpful to write test code in a more imperative formalism than the implementation, because when these two styles of code agree, it increases our confidence that we interpreted musical concepts faithfully.
 
Lastly, counterpoint translates faithfully into our Dusa formalism in part because counterpoint is a \emph{formalist} style of music, defined by strict rules.
In contrast, the motivations underlying those rules are often given in emotional terms: tension, resolution, smoothness, and the like.
This subjective aspect of music should not be expected to translate smoothly into computational formalism. 
Rather, our co-creativity approach allows software to enforce formal constraints within which a user exercises their subjectivity.

\paragraph{RQ2: How does development of a mixed-initiative creative  interface with familiar 
    composition affordances interdepend with the development of the Dusa backend solver?}

The JavaScript API provided by Dusa enables integration to be performed just once, invoking the Dusa solver in a worker thread.
The frontend and backend were able to evolve in a modular fashion throughout development because of the stable interface between them: the frontend specifies a cantus firmus and rule set, from which the backend generates a counterpoint.
We expect stable output interfaces to be common for procedural generation tasks where the ``medium'' is fixed, though input interfaces may evolve as configuration options are added.

A more subtle design consideration, however, is the extent to which seeing program internals on the user interface is \emph{desirable}.
CounterChoice is specifically intended as a \emph{demonstrator} application for Dusa, which must balance the competing needs to provide familiar affordances and showcase technical novelties.
To ensure familiarity, the ``programmability'' of CounterChoice is restricted to selecting a rule set.
Deeper interaction with Dusa code is delayed until after the main interaction is complete, as optional code download is offered only after a complete counterpoint has been generated.
Without rule set selection, the interface would provide no direct intuition for the underlying generation model; 
without a direct manipulation GUI, the audience may be restricted to users of research programming languages.

Though Dusa integration did not impose much burden on frontend development, it also did not make our frontend development \emph{easier}.
The largest section of frontend code is dedicated to the bespoke direct-manipulation piano roll interface, which must handle various GUI events and render graphics in detail.
The decision to adopt a language like Dusa must be made with proper awareness of its scope: if the backend generation algorithms are a minority of the codebase, a minority of code will change when Dusa is adopted.

\paragraph{RQ3: How can the experience of developing CounterChoice 
    inform design and implementation of programmer experience for logic 
    programming languages, in the context of constraint solving for an artistic
    practice?}

Dusa is only one logic programming language among many, so we elaborate our Dusa experience into design and implementation recommendations for logic programming tools in general.
By necessity, echoes of timeless advice are visible in our recommendations, but we make this advice more concrete by focusing on a specific gap in the state of language implementation.
In imperative programming, breakpoint debugging provides a standardized model for the user experience of debuggers, but limited debugging tools exist for logic languages, let alone a standardized user experience.
In reflecting on the development experience, we wish to better understand desirable modes of programmer interaction for logic programming debuggers.
The examples provided with each recommendation are meant to help convey the contents of the recommendation; further research is required to identify which example measures are effective.

In Dusa, the semantics of a logic program is a search space.
This interpretation plays out when debugging performance issues.
During one test, our mental model predicted only a few hundred states, but Dusa measured millions of states explored.
Beyond counting explored states, programmers need insight into which states were explored and why.
Traditional interfaces focus on displaying successful solutions, but this is inadequate for debugging, where proof search explored millions of failing states outside the intended search space. 
Understanding this failing space is essential to understanding buggy program behavior, yet it is hard to understand with current tools both because the states fail and because they are vast in number.
%These states, where search failed, did not contribute to the final solution set, which was as small as predicted.
%Logic programs excel at automatically searching large search spaces that emerge from small rule sets, but the failed branches of search are just as important to understanding overall program behavior as successful branches are.
%There are often millions of such failed branches, far more than a human programmer can efficiently inspect by hand.
\emph{Design Recommendation:} Provide scalable means to inspect space of intermediate search states, especially failing states.

\emph{Examples:} For each solution, allow rewinding its proof step-by-step. At each step, show alternative branches and indicate which ones fail. 
For large state spaces, display a limited set of intermediate and failing spaces.
Select these sets to maximize the variety of rules applied in intermediate states and the variety of predicates present in failing states.

The search space semantics of Dusa is equally present in debugging for correctness.
Substantial time was spent debugging rules which never activated because typos resulted in never-true premises.
Unreachable code is often detected statically in imperative and functional languages, but the search-based nature of logic programs means reachability information is incomplete until runtime.
We thus recommend hybrid static-dynamic checking.
%In imperative languages, warnings for these unreachable statements are widespread.
%In functional programming languages, strong type systems are commonly provided which rule out broad classes of errors before execution.
%Because logic programs are search-based, reachability information is limited until runtime, and static computations of reachability may need to rely on approximations.
\emph{Design Recommendations:} Provide hybrid static-dynamic unreachable code detection mechanisms.

\emph{Examples:} Statically detect premises containing undefined predicates (typos). Statically compute a predicate dependency graph to identify provably-unreachable predicates. 
Dynamically report rules that occur nowhere in the search space or solution space. Report never-satisfied premises of such rules.

It is timeless advice to avoid premature optimization.
In Dusa, this means prioritizing application-level optimization of the search space over the performance of primitive search operations.
The Dusa implementation is not heavily optimized.
With no changes to this Dusa, improvements to the design of CounterChoice's core rule set increased the length of supported compositions 
from about 12 notes to 50 notes, because  small rule changes can greatly reduce search space size.
\emph{Design Recommedation:} To support optimization, support identification of search space redundancies.

\emph{Examples:} Display multiple search paths that led to the same solution. Allow the programmer to indicate which predicates represent a program's final output, then identify multiple solutions corresponding to an identical final output.

Search space optimization is subtle in particular because Dusa's search is randomized, as appropriate for procedural content generation.
However, different random seeds greatly impact explored state counts and running times, so that it is not always clear whether a given change improved performance.
This randomness must be accounted for debugging mechanisms.
\emph{Design Recommendation:} Build randomization into the debugging process.

\emph{Examples:} Allow fixing a random seed to better measure effects of a given change. Run the same program on multiple seeds and visualize the distribution of performance results.

The common theme between all our recommendations is that logic programming is programming with possibility spaces, so debugging should be conceptualized at the space level as well.

\subsection{Alternative Algorithm: Divide-and-Conquer}
%\CA{This subsection was moved here from Section~\ref{sec:dusa-implementation}.}
CounterChoice, as implemented, has successfully addressed our research questions.
However, it is important to recognize that alternative design and implementation decisions are possible.
To this end, we explore an alternative divide-and-conquer algorithm which we prototyped during the development process before settling on the algorithm documented in Section~\ref{sec:dusa-implementation}.

Though the CounterChoice implementation can solve cantus firmi of 50 notes, its exponential complexity is a clear limitation for long pieces.
To handle such cases, we developed an alternative \emph{divide-and-conquer} approach using JavaScript where the cantus firmus is divided into overlapping segments based on index boundaries, each one is solved independently by the Dusa solver, and the results are assembled into a complete counterpoint line. 
The strength of this approach is that bounding the length of each segment bounds the extent of exponential slowdown.
The divide-and-conquer approach has a natural musical motivation as well; composers often work phrase by phrase rather than treating every note with equal global importance.
Despite these strengths, the key conceptual weakness of the divide-and-conquer approach is that it cannot claim to be fully implemented in Dusa, relying extensively on JavaScript code that invokes the Dusa solver repeatedly and assembles its outputs.

\paragraph{Segment Indices}

The solver starts by deciding on the indices of the cantus firmus line to be divided into segments. Segment and overlap size are defined using \verb|CHUNK_SIZE| and \verb|OVERLAP| respectively, which are set to be 10 and 4. For each segment until the last, indices from the starting index to the starting index plus \verb|CHUNK_SIZE| are selected, and the next segment's starting index is incremented by $\verb|CHUNK_SIZE|-\verb|OVERLAP|$ (e.g. the first segment is [0-9], the second one is [6-15]). When remaining indices are fewer than \verb|OVERLAP|, they are added into the last segment's indices to prevent creating a short segment at the end. Later, cantus firmus notes of the selected indices are extracted from the input, and the solver is run on each segment separately using local indexing.

\paragraph{Overlapping Segments}

Horizontal constraints spanning consecutive time steps require special care at segment boundaries. The overlap size \verb|OVERLAP| is chosen to be 4 to ensure consecutive segments abide by the \emph{no more than three leaps} rule. Since the predicate \verb|fourLeaps| checks the next time steps up to \verb|T+4|, we insert the \verb|cp| values found by the solver for segment \verb|i+1| to the end of the input as closed facts directly into the Dusa solver for segment \verb|i|. The order of calling the solver is from the last segment to the first.
\begin{verbatim}
for (let i = 0; i < fixedCp.length; i++) {
    inputCf += `cp ${fixedCpStartLocal + i} is
    ${fixedCp[i]}.\n`;
}
\end{verbatim}

Writing these as closed facts prevents the solver from reconsidering those steps and avoids duplicate solutions in the overlapping region.

\paragraph{Specialized Solvers}

Because certain constraints apply only at specific positions in the melody, namely the starting and ending interval rules, prohibition on unisons in the middle, and the cadence rule, we adapted \texttt{counterpoint\_opt.du} into three variant Dusa solvers for the beginning, middle, and ending segments respectively, each enforcing only the constraints appropriate to its position.

Calls to the Dusa solver are made with a function named \verb|solveChunk|, which takes parameters such as the current segment, segment's type, and fixed \verb|cp| values. Inside \verb|solveChunk|, calls to Dusa files are made using the \verb|execFileSync| function from the \verb|child_process| module to enable interruptions if no solutions are found. The maximum number of attempts per segment and the timeout limit are set to 5 and 2000ms respectively.

\paragraph{Findings}
The approach performed well in practice, solving one segment in approximately 224ms on average with a chunk size of 10, and scaling linearly with the number of segments.
However, the current implementation does not employ a backtracking mechanism, which means the main failure mode is that the solver occasionally gets stuck on a random segment. Although the performance is very promising, the implementation described in Section~\ref{sec:dusa-implementation} can already generate counterpoint melodies with 50 notes, which is already sufficient for all compositions the authors wished to develop.
Between the architectural complexity of the divide-and-conquer algorithm and the observed failure mode, we did not investigate it further.

Nonetheless, the divide-and-conquer implementation holds several takeaway lessons.
We learned that generation of long counterpoints should not be dismissed as exponentially complex when a subexponential algorithm exists that not only generates correct counterpoints in principle but interesting ones in practice.
The existence of this substantially different algorithm also highlights that counterpoint generation is not a creative process for the end user alone; rather there is substantial space available for creativity in the design and implementation of counterpoint generation algorithms themselves.
