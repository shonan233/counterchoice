\subsection{Research Questions}
We structure the discussion of our experience building and using CounterChoice around our research questions.
We answer each question in turn by synthesizing the empirical results of the development process with the authors' qualitative experiences as the developers.

\paragraph{RQ1: How faithfully is the established musical formalism of counterpoint reflected in the computational formalization of counterpoint as ``executable knowledge'' in a Dusa program?}
At the top-level, the Dusa formalism is structured as \verb|#forbid| and \verb|#demand| constraints.
These constraints match the formalism of natural-language counterpoint rules directly, which define patterns that must or must not occur.

Dusa formalism and counterpoint formalism differ primarily in their depth.
As a natural-language description, the rules of counterpoint can freely assume domain knowledge: the intended readers understand the concepts of notes, intervals, modes, and direct vs.\ contrary motion.
Dusa is not a domain-specific language, so these notions must be implemented explicitly.
The implementation in Dusa was concise precisely because the domain concepts can be built up readily from concepts native to Dusa, such as finite types and natural numbers.

Students of music theory traditionally prefer to use one formalism at a time, providing a unified guiding structure for the composition.
In contrast, we need to ensure that the Dusa implementation of counterpoint concepts is faithful.
We found it helpful to write test code in a more imperative formalism than the implementation, because when these two styles of code agree, it increases our confidence that we interpreted musical concepts faithfully.
 
Lastly, counterpoint translates faithfully into our Dusa formalism in part because counterpoint is a \emph{formalist} style of music, defined by strict rules.
In contrast, the motivations underlying those rules are often given in emotional terms: tension, resolution, smoothness, and the like.
This subjective aspect of music should not be expected to translate smoothly into computational formalism. 
Rather, our co-creativity approach allows software to enforce formal constraints within which a user exercises their subjectivity.

\paragraph{RQ2: How does development of a mixed-initiative creative  interface with familiar 
    composition affordances interdepend with the development of the Dusa backend solver?}

The JavaScript API provided by Dusa enables integration to be performed just once, invoking the Dusa solver in a worker thread.
The frontend and backend were able to evolve in a modular fashion throughout development because of the stable interface between them: the frontend specifies a cantus firmus and rule set, from which the backend generates a counterpoint.
We expect stable output interfaces to be common for procedural generation tasks where the ``medium'' is fixed, though input interfaces may evolve as configuration options are added.

A more subtle design consideration, however, is the extent to which seeing program internals on the user interface is \emph{desirable}.
CounterChoice is specifically intended as a \emph{demonstrator} application for Dusa, which must balance the competing needs to provide familiar affordances and showcase technical novelties.
To ensure familiarity, the ``programmability'' of CounterChoice is restricted to selecting a rule set.
Deeper interaction with Dusa code is delayed until after the main interaction is complete, as optional code download is offered only after a complete counterpoint has been generated.
Without rule set selection, the interface would provide no direct intuition for the underlying generation model; 
without a direct manipulation GUI, the audience may be restricted to users of research programming languages.

Though Dusa integration did not impose much burden on frontend development, nor can it make frontend development \emph{easier}.
The largest section of frontend code is dedicated to the bespoke direct-manipulation piano roll interface, which must handle various GUI events and render graphics in detail.
The decision to adopt a language like Dusa must be made with proper awareness of its scope: if the backend generation algorithms are a minority of the codebase, a minority of code will change when Dusa is adopted.

\paragraph{RQ3: How can the experience of developing CounterChoice 
    inform design and implementation of programmer experience for logic 
    programming languages, in the context of constraint solving for an artistic
    practice?}

Because Dusa is only one logic programming language among many, we elaborate our Dusa experience into design and implementation recommendations for logic programming-based creativity tools overall.

The Dusa language implementation is not heavily optimized for performance.
It is a timeless adage that premature optimization should be avoided, but the CounterChoice adage bore this out.
With no changes to the Dusa language implementation, improvements to the design of CounterChoice's core rule set increased the length of supported compositions from about 12 notes to nearly 50 notes, which is a substantial increase in the context of exponential search complexity.
\emph{Implementation Recommendation:} In accordance with timeless advice, avoid premature optimization.

Though the optimization process required no changes to the language implementation, the same optimization process revealed usability limitations in the programmer experience.
Procedural content generation fundamentally values diversity of generated content, so Dusa's use of randomized search is an appropriate default behavior.
However, the running time of search can vary drastically between random seeds, making the impact of optimizations difficult to measure.
Likewise, buggy behavior may appear only for certain random seeds, making it more difficult to measure whether a given revision resolves a bug during the debugging process.
\emph{Design Recommendation:} Provide the option to manually seed the random number generator for performance testing and debugging.

Dusa provides performance metrics such as the number of states explored.
During optimization, we measured progress using these metrics, but observed that millions of states were explored when our mental model predicted only a few hundred.
These states, where search failed, did not contribute to the final solution set, which was as small as predicted.
Logic programs excel at automatically searching large search spaces that emerge from small rule sets, but the failed branches of search are just as important to understanding overall program behavior as successful branches are.
There are often millions of such failed branches, far more than a human programmer can efficiently inspect by hand.
\emph{Design Recommendation:} 
  Provide mechanisms for inspecting the failing and intermediate regions of the search space. 
  Present a bounded volume of information even when large state sets are explored.

Substantial time was spent debugging rules which never activated because their premises are never satisfied, e.g., due to typos.
In imperative languages, warnings for these unreachable statements are widespread.
In functional programming languages, strong type systems are commonly provided which rule out broad classes of errors before execution.
Because logic programs are search-based, reachability information is limited until runtime, and static computations of reachability may need to rely on approximations
\emph{Design Recommendations:} Establish static warnings to detect classes of logic programs that are highly unlikely to reflect programmer intention.

\subsection{JavaScript tooling}

\CA{This subsection was moved here from Section~\ref{sec:dusa-implementation}.}

We rewrote the Dusa program multiple times throughout the project, adding more rules of counterpoint, correcting bugs, and improving its performance. In addition to our main web frontend (Section~\ref{sec:ui-implementation}), we developed a handful of small command-line scripts around our Dusa code to help us improve and debug it throughout the process.

These tools are written in JavaScript using the Dusa API, and generally append an input cantus firmus---represented as a list of \verb|cf T is N| and \verb|length is T| facts---to a Dusa program implementing the rules of counterpoint (e.g., as described in Section~\ref{sec:dusa-implementation}).

\paragraph{MIDI output}

On the same day we started the CounterChoice project, we wrote a JavaScript tool which combines the cantus firmus and generated counterpoint melody into a MIDI file. Rendering Dusa solutions as audio made the output much more tangible, and provided a simple way to check whether the output is sensible.

\paragraph{Validation}

For more detailed validation, we wrote a script that checks whether the \verb|cf T| and \verb|cpNote T| facts in a Dusa solution satisfy the rules of counterpoint specified in JavaScript using simple \verb|for| loops, etc. We caught multiple bugs in our logic this way, and it was at times helpful to have a very different ``reference implementation'' of the rules.

\paragraph{Regression testing}

One shortcoming of the above validation strategy is that it can detect \emph{soundness} bugs in which our Dusa implementation allows an invalid counterpoint melody, but not \emph{completeness} bugs in which our Dusa implementation is overly conservative. For instance, it cannot detect whether our Dusa implementation only generates a single (correct) counterpoint melody.

As we experimented with multiple Dusa implementations, we found it useful to perform a simple form of ``regression testing'' in which we generated solutions with one Dusa implementation and checked whether a second Dusa implementation accepts that solution. (More precisely, we asked Dusa whether the second implementation appended with the first solution has any solutions.) This script caught some early bugs in the implementation described in Section~\ref{sec:dusa-implementation}.

\paragraph{Benchmarking}

Although runtime performance is not paramount here, we found that different ways of phrasing the constraints within Dusa had dramatic impacts on the time to first solution, and importantly, the length of cantus firmus for which we could find a solution before running out of memory. (Indeed, the search space is exponential.)

An early version of our Dusa code based around a monolithic \verb|judgeCP T I is {good,bad}| predicate got stuck on cantus firmi longer than about 12 notes. Reworking this around separate \verb|#forbid|den predicates increased the limit to over 30 notes, and further refinements allow our current implementation to solve cantus firmi with close to 50 notes.

While fine-tuning the implementation, we found it helpful to write a simple script which measures the amount of time it takes Dusa to compute a first solution for the same cantus firmus across multiple trials, given that Dusa is nondeterministic. We also experimented with setting the RNG seed at the start of this script, so that the benchmark itself would return the same results across multiple runs.


\subsection{Alternative Approach: Divide-and-Conquer}

\CA{This subsection was moved here from Section~\ref{sec:dusa-implementation}.}

Although our implementation is capable of producing solutions for cantus firmi of up to 50 notes, the exponential nature of the search space means it eventually reaches practical limits for longer pieces. To handle such cases, we developed an alternative divide-and-conquer approach using JavaScript where the cantus firmus is divided into overlapping segments based on index boundaries, each one is solved independently by the Dusa solver, and the results are assembled into a complete counterpoint line. This approach also has a natural musical motivation; composers often work phrase by phrase rather than treating every note with equal global importance.

\paragraph{Segment Indices}

The solver starts by deciding on the indices of the cantus firmus line to be divided into segments. Segment and overlap size are defined using \verb|CHUNK_SIZE| and \verb|OVERLAP| respectively, which are set to be 10 and 4. For each segment until the last, indices from the starting index to the starting index plus \verb|CHUNK_SIZE| are selected, and the next segment's starting index is incremented by $\verb|CHUNK_SIZE|-\verb|OVERLAP|$ (e.g. the first segment is [0-9], the second one is [6-15]). When remaining indices are fewer than \verb|OVERLAP|, they are added into the last segment's indices to prevent creating a short segment at the end. Later, cantus firmus notes of the selected indices are extracted from the input, and the solver is run on each segment separately using local indexing.

\paragraph{Overlapping Segments}

Horizontal constraints spanning consecutive time steps require special care at segment boundaries. The overlap size, \verb|OVERLAP| is chosen to be 4 to ensure consecutive segments abide by the \emph{no more than three leaps} rule. Since the predicate \verb|fourLeaps| checks the next time steps up to \verb|T+4|, we insert the \verb|cp| values found by the solver for segment \verb|i+1| to the end of the input as closed facts directly into Dusa solver for segment \verb|i|. The order of calling the solver is from the last segment to the first.
\begin{verbatim}
for (let i = 0; i < fixedCp.length; i++) {
    inputCf += `cp ${fixedCpStartLocal + i} is
    ${fixedCp[i]}.\n`;
}
\end{verbatim}

Writing these as closed facts prevents the solver from reconsidering those steps and avoids duplicate solutions in the overlapping region.

\paragraph{Specialized Solvers}

Because certain constraints apply only at specific positions in the melody, namely the starting and ending interval rules, prohibition on unisons in the middle, and the cadence rule, we adapted \texttt{counterpoint\_opt.du} into three variant Dusa solvers for the beginning, middle, and ending segments respectively, each enforcing only the constraints appropriate to its position.

Calls to the Dusa solver are made with a function named \verb|solveChunk|, which takes parameters such as the current segment, segment's type, and fixed \verb|cp| values. Inside \verb|solveChunk|, calls to Dusa files are made using the \verb|execFileSync| function from \verb|child_process| module to enable interruptions if no solutions are found. Maximum number of attempts per segment, and timeout limit is are set to 5 and 2000ms respectively.

\paragraph{Findings}

The approach performed well in practice, finding solutions to given cantus firmi almost instantly regardless of length. However, the current implementation does not employ a backtracking mechanism, which means the main failure mode is that the solver occasionally gets stuck on a random segment. Although very promising, due to the optimizations described in Section~\ref{sec:dusa-implementation} raising the practical limit of the standard implementation to close to 50 notes, we did not pursue this direction further.
